# What's Changed

## New Features

### Async.chunk

Processing thousands of records in the background used to mean a `Database.Batchable` (heavier, separate lifecycle) or one job per record (blows limits, no coordination). `Async.chunk` pages a data set across chained Queueables, with the same per-job tracking, retry and backoff as any other `QueueableJob`.

```apex
Async.chunk(new AccountRecalcJob(), ChunkSource.of(records))
    .chunkSize(50)
    .retry(2)
    .enqueue();

// sets too large to hold in memory, via a SOQL cursor
Async.chunk(new AccountRecalcJob(), ChunkSource.query('SELECT Id FROM Account WHERE ...'))
    .chunkSize(200)
    .enqueue();
```

A run is a first-class chain member, not a parallel feature. It takes one slot in the chain, so `JOB1 -> chunk run -> JOB3` runs JOB3 only after the last page. Priority still wins, so a higher-priority job added mid-run preempts the next page and the run resumes afterwards. `dependsOn(...)` resolves against the outcome of the whole run: `.succeeded()` means every page passed.

The source is pluggable through `ChunkSource`, which mirrors `Database.Cursor` with `getNumRecords()` and `fetch(position, count)`, so you can supply your own. Your job keeps its own members across pages, which gives you `Database.Stateful` behaviour without asking for it.

Runs chain to each other with `ChunkBuilder.chunk(...)`, so a multi-stage pipeline stays fluent and `dependsOn(Async.afterPrevious())` reads the previous run's outcome as a whole.

A cursor source takes an explicit `AccessLevel`, defaulting to `SYSTEM_MODE`. The framework always passes one rather than inheriting the platform default, which is system mode up to API 66.0 and user mode from 67.0; inheriting it would have quietly changed which rows a run sees on an API bump.

`.stopRemainingChunksOnFailure()` halts a run when a page exhausts its retries, and a run that ends early records one summary `AsyncResult__c` naming the page it stopped at and how much work was left. See [Chunk API](https://async.beyondthecloud.dev/api/chunk) (#47).

### onFinalFailure

Reacting to a job that failed for good meant writing a separate finalizer job, which cannot see a failure that `continueOnJobExecuteFail` swallowed and knows nothing about the retry decision. `onFinalFailure` fires **once per job**, only when it will not run again.

```apex
public class SyncContactsJob extends QueueableJob {
  public override void work() { /* ... */ }

  public override void onFinalFailure(Async.FailureContext failureCtx) {
    switch on failureCtx.retryOutcome {
      when EXHAUSTED     { escalate(failureCtx.retryHistory); }
      when NOT_RETRYABLE { raiseBug(failureCtx.failure); }
      when else          { log(failureCtx); }
    }
  }
}
```

`Async.RetryOutcome` tells a transient outage from a bug: `NOT_CONFIGURED` (no retry policy), `NOT_RETRYABLE` (your `retryOn` filter or `isRetryable` refused it) and `EXHAUSTED` (retried to the cap and still failing). The context also carries the exception type, message and **stack trace**, plus `retryHistory`, which is the only place the intermediate attempts are recorded.

It fires once per failed page of a chunk run, and a throwing override is recorded in `RetryHistory__c` rather than killing the chain. See [onFinalFailure](https://async.beyondthecloud.dev/api/queueable#onfinalfailure).

### AsyncMock.whenQueueable(...).thenThrow(...)

Any job can now be failed from a test without writing a job class that throws, mirroring the finalizer mock. The mocked failure settles through the same path a real one does, so rollback, retry classification and result recording all apply.

## Improvements

- Jobs of equal priority now run in the order you chained them. `List.sort()` does not define the order of equal elements, so this was previously accidental rather than guaranteed.

## Bug Fixes

- **A retry no longer duplicates work.** A retry re-runs `work()`, which re-registers whatever that attempt added to the chain. Nothing discarded the failed attempt's additions, so a finalizer attached with `attachFinalizer()` or a follow-up job added with `.chain()` was queued once per attempt and executed N times. With `.retry(2)` that meant three copies of real business work, silently. The failed attempt's chain additions are now discarded before the retry is queued, the same way `rollbackOnJobExecuteFail` discards its DML.

  Worth knowing: if attempt 1 registers a finalizer and attempt 2 throws before reaching `attachFinalizer()`, that finalizer no longer runs. Retry bookkeeping is untouched, `RetryAttempts__c`, `RetryHistory__c` and `ExceptionMessage__c` still carry every attempt.

- Clean URLs on the docs site.
- Dependency bumps (npm), resolving Dependabot security alerts in the docs toolchain.
