# What's Changed

## Breaking Change: jobs must say what happens to their state between runs

**Everyone using `retry(n)` or `Async.chunk(...)` has to make a one-line change.** The upgrade
installs cleanly; the change is needed before those jobs will enqueue.

### Why

A job object can run more than once. A retry re-runs it, and a chunk run re-runs it once per
page. Both times it kept whatever the previous run left on it, silently:

```apex
public class ImportJob extends QueueableJob {
    private List<Id> inserted = new List<Id>();

    public override void work() {
        for (Account a : accounts) {
            insert a;
            inserted.add(a.Id);
        }
        publish(inserted);   // attempt 2 publishes attempt 1's ids too
    }
}
```

Attempt 1 inserts 50 records and throws. Attempt 2 starts with 50 ids already in `inserted`,
adds 50 more, publishes 100, and reports success. `resetForRetry()` existed for this but nothing
made you use it.

### What to do

Pick one per job. Clear your own state, or have Async Lib replay the job from the state it had at
enqueue:

```apex
public class ImportJob extends QueueableJob implements Async.Retryable {
    public void resetBeforeRetry(Integer attempt) {
        inserted.clear();
    }
}
```

```apex
Async.queueable(new ImportJob()).retry(3).restoreStateOnRetry().enqueue();
```

Chunk runs get the same pair, `Async.ChunkResettable` with `resetBeforeNextChunk(Integer)`, or
`restoreStateOnNextChunk()`, because a job may keep a running total across pages while still
wanting a clean slate when a page is retried.

**An empty body is a valid answer** and keeps the 2.x behaviour on purpose. The change is that you
decide it.

### Where it fails

At `.enqueue()` or `.chain()`, synchronously, in your own transaction, so in your existing tests
on a sandbox rather than in production. The message names both options with the right prefix for
your org. Retry turned on through `QueueableJobSetting__mdt` does not throw: it is not applied to
a job that declares no reset, and the reason is recorded.

### `resetForRetry()` is superseded

No longer called. Move its body into `resetBeforeRetry(Integer attempt)` and declare
`implements Async.Retryable`. The method stays as a no-op because removing a `global` member
breaks the package install in every org that referenced it.

See [Job State Between Runs](https://async.beyondthecloud.dev/explanations/job-state-between-runs).

## New Features

### Requeue a failed job from its `AsyncResult__c` record

A job failed, you fixed the cause, run it again with the same input:

```apex
Async.requeue(resultId);
Async.RequeueSummary summary = Async.requeue(failedResultIds);
```

The snapshot is the job as **enqueued**, not as the failed attempt left it. Off until you turn it
on with `StoreJobPayload__c = Yes`, because a payload is a copy of the job's data; a job record can
say `No` against an org-wide `Yes`. It does not need `CreateResult__c`: storing a payload writes a
row for failed and skipped jobs regardless, never for successful ones. Bulk replays run as one
chain, each replay linked back by `RequeuedFrom__c`, and the source is marked `Requeued` so a
scheduled replay never picks a row up twice.

Four new fields on `AsyncResult__c`: `JobPayload__c`, `PayloadSize__c`, `RequeueStatus__c`,
`RequeuedFrom__c`.

Installed as a package? JSON cannot cross a namespace boundary in either direction, so the
snapshot has to be written and read in your namespace: copy `extras/classes/AsyncJobSerializer.cls`
and name it in `JobSerializerClass__c` on the `All` record. One class per org. A source deploy
needs nothing.

**Requeue replays data, not intent.** A renamed field arrives `null`; a field that changed
meaning replays the old data under the new meaning, silently. If the fix changed the job's own
fields, enqueue it fresh. Not permission-gated, like every other `Async` call; if you put it behind
a button, check a custom permission in your controller first.

See [Requeue](https://async.beyondthecloud.dev/explanations/requeue).

### Pluggable logger and job lifecycle events

Register one class and every async job in the org reports to it:

```apex
global class AsyncJobLogger implements Async.OnJobFailed {
    public void onJobFailed(Async.FailureContext ctx) {
        Logger.error('Async job failed: ' + ctx.className, ctx.failure.message);
        Logger.saveLog();
    }
}
```

Set `LoggerClass__c` to `AsyncJobLogger` on the `All` record of `QueueableJobSetting__mdt`.

| Interface | Fires |
| --------- | ----- |
| `Async.OnJobEnqueued` | a job is added to a chain |
| `Async.OnJobSucceeded` | a job finished without failing |
| `Async.OnJobFailed` | a job failed with no attempts left |
| `Async.OnRetryEnqueued` | an attempt failed and another is queued |

Implement only what you need. The same interfaces work directly on a `QueueableJob` for one-off
reactions. **The registered class must be `global`**, because Async Lib resolves it by name from
its own namespace; the methods stay `public`. A listener that throws never affects the job, and
an unresolvable name degrades to no logging with the reason recorded.

`info(key, value)` on the builder attaches metadata that arrives on every context, so alerts can
be routed by team or package. `Async.FailureContext` gains `nextAttemptDelayMinutes`. See
[Logging](https://async.beyondthecloud.dev/explanations/logging).

### `restoreStateOnRetry()` and `restoreStateOnNextChunk()`

Async Lib takes a deep copy of the job at enqueue and replays from it. Only the fields **you**
declared are restored; `retryAttempt`, the retry history, the backoff delay and the chunk position
carry forward. The copy costs roughly twice the job's size in heap while it is made. Prefer the
hooks when your reset is a couple of `clear()` calls.

Installed as a package? The copy has to be made in your namespace, so extend `BaseQueueableJob`
from `extras/` instead of `btcdev.QueueableJob`. A source deploy needs nothing.

### `BaseChunkJob`

For packaged installs only: `extras/classes/` gains `BaseChunkJob`, the chunk counterpart of
`BaseQueueableJob`, so `restoreStateOnNextChunk()` works on a chunk job the same way. Extend it
instead of `btcdev.ChunkJob`. `BaseQueueableJob.AllowsCallouts` is gone from the template;
callouts are declared with `implements Database.AllowsCallouts` on any base.

### `Async.Backoff` for retry settings inside the job class

Inside a `QueueableJob` subclass the inherited `backoff` field shadows the `Backoff` type, so
`Backoff.exponential(1)` does not compile there. `Async.Backoff` exposes the same factories:

```apex
public SyncJob() {
    this.maxRetries = 5;
    this.backoff = Async.Backoff.exponentialWithJitter(1);
}
```

See [Configuring backoff inside the job class](https://async.beyondthecloud.dev/api/queueable#configuring-backoff-inside-the-job-class).

### `AsyncMock.jobSettings(...)`

Custom Metadata cannot be inserted in Apex, so none of the `QueueableJobSetting__mdt` behaviour
was testable by a consumer until now:

```apex
AsyncMock.jobSettings(new List<QueueableJobSetting__mdt>{
    new QueueableJobSetting__mdt(QueueableJobName__c = 'All', LoggerClass__c = 'MyAsyncLogger', MaxRetries__c = 2)
});
```

Covers every setting. `AsyncMock.reset()` clears them.

## Changed guidance: declaring callouts

Use the platform marker, `implements Database.AllowsCallouts`, on any job that calls out. It
composes with any base class, including `ChunkJob` and the packaged bases, so there is one way
for every job type. `extends QueueableJob.AllowsCallouts` still works; nothing to change in
existing code.

## Fixed

### A failed attempt no longer leaks chain changes into the next one

Jobs chained inside `work()`, and `stopChain()` / `skipJob()` calls, only touched the chain in
memory, so a rollback never undid them: a job whose DML was rolled back still ran the jobs it had
chained. An attempt that did not commit now leaves the chain as it found it, matching what
Salesforce does for a plain `System.enqueueJob`. Attached finalizers are kept. See
[What a Failed Job Does to the Chain](https://async.beyondthecloud.dev/explanations/failures-and-the-chain).

### `deepClone()` with `retry()` silently never retried

The clone failed inside the finalizer, where nothing surfaces an exception, so the job ran once,
reported `Completed`, and never retried. The clone now works from a stripped copy, and a clone
that still fails settles the job with the reason in `RetryHistory__c`. Any fault inside the
framework's own finalizer now writes an `AsyncResult__c` row with `Status__c = FRAMEWORK_ERROR`,
even when `CreateResult__c` is off.

### One Custom Metadata typo could stop every job in the org

`MaxRetries__c` above the cap, an unknown `BackoffStrategy__c`, or retry turned on for a job with
no declared reset each threw from enqueue, and the `All` record reaches every job. Each now
degrades to the safe behaviour and records why in `RetryHistory__c`. Mistakes written in Apex
still throw. See [Configuration Safety](https://async.beyondthecloud.dev/explanations/configuration-safety).

### `className` is no longer recomputed on every hop

It was `transient`, so every transaction recomputed it for every job in the chain by throwing and
catching a `TypeException`. It is serialized once now.

### Page layouts were missing almost every field

`AsyncResult__c` showed 4 of its 15 fields, without `Status__c` or `ExceptionMessage__c`;
`QueueableJobSetting__mdt` showed 3 of 8. Every field is on its layout now, grouped, with related
lists for `DependsOnResult__c` and `RequeuedFrom__c`.
