# What's Changed

## New Features

### Batch failures are recorded, logged and can be run again

Add `Database.RaisesPlatformEvents` to a batch and every failed scope lands on `AsyncResult__c`,
governor limit errors included, with the ids of the records that were in it. The class in
`LoggerClass__c` hears about it through the `Async.OnJobFailed` it already implements.

```apex
public class AccountSyncBatch implements Database.Batchable<SObject>, Database.RaisesPlatformEvents {
    // start, execute, finish exactly as before
}
```

Once the cause is fixed, run just the failed records again, through the batch's own `execute()`:

```apex
Async.requeueBatchFailures(
    new AccountSyncBatch(),
    failedBatchJobId,
    new List<SObjectField>{ Account.Name, Account.Industry }
);
```

The third argument says what to reload, because a failure stores ids, not records. Pass fields,
field paths as strings for parent fields (`'Owner.Email'`), or an `Async.BatchRecordLoader` for
anything else. A scope that fails again stays open and can be requeued again.

Recording follows `CreateResult__c`, on `All` or on a record named after the batch class.
[Batch Failures](https://async.beyondthecloud.dev/explanations/batch-failures)

### `Async.queueable().enqueue()` starts what other code chained

Several services can each call `chain()`, and the entry point starts everything with one line:

```apex
Async.queueable(new SendWelcomeJob(accountIds)).chain();   // AccountService
Async.queueable(new ReviewContactJob(contactIds)).chain(); // ContactService

Async.queueable().enqueue();                                // entry point, last line
```

Before 3.1.0 that last line did nothing and both jobs were dropped without an error. It still does
nothing when nothing is waiting, so it is safe to call from an entry point that does not know
whether any service had work.
[Chaining Across Services](https://async.beyondthecloud.dev/explanations/chaining-across-services)

## Improvements

- `Async.FailureContext` carries `asyncType` and `salesforceJobId` for every failure, and
  `batchPhase`, `batchScope` and `batchScopeTruncated` for a batch failure.
- `AsyncResult__c` has three new fields for batch failures: `BatchPhase__c`, `BatchScope__c` and
  `BatchScopeTruncated__c`. They are on the layout and in the `AsyncResultAccess` permission set.
- `Async.requeue(resultId)` on a batch failure row explains that it needs
  `Async.requeueBatchFailures` instead of reporting a missing payload.

## Bug Fixes

- A chunk run over an empty source no longer breaks `dependsOn(Async.afterPrevious())` for the
  job chained after it. The empty run vanishes and "previous" stays the job before it.
- Every Apex class carries the MIT license header and the library version, so a copied file can be
  traced to its release. `LICENSE` names Beyond The Cloud Sp. z o.o.

## Behaviour change to check

`Async.queueable().enqueue()` used to be a no-op in every case. It now starts jobs that were
chained earlier in the same transaction and never enqueued. Code that relied on those jobs being
dropped was already broken, but it will behave differently: the jobs run.
